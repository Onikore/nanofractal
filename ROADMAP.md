# Roadmap

Рабочий план развития nanofractal после 0.6.1. Источники: собственный анализ и
внешний отчёт по тестам на Raspberry Pi 5 (autolanding-pi, задачи помечены
`[ext P…]`). Отмечаем `[x]` по мере выполнения, в коммитах ссылаемся на номер
задачи (например `R2`). План испытаний на Pi — в [RPI_TEST_PLAN.md](RPI_TEST_PLAN.md).

## Правила для каждой задачи

1. **Скорость меряем, не угадываем:** `benchmarks/fractal_bench.py run --vs base.json`
   (1 ядро: `--threads 1`, все ядра: `--threads 0`), до/после — в описании.
2. **Качество не ухудшаем:** `benchmarks/robustness.py --json` до и после,
   разница — в описании. Изменение поведения допустимо только осознанно и с
   записью в CHANGELOG.
3. **Углы внешних маркеров остаются бит-в-бит** с эталоном
   (`tests/test_reference_equivalence.py`), если задача явно не меняет
   алгоритм — тогда эталонный тест обновляется вместе с обоснованием.
4. Перед пушем: `pre-commit run --all-files`, полный `pytest`, при изменении C++ —
   прогон под ASan (`-DNF_SANITIZE=ON`), сборка под OpenCV 4.10 и 5.
5. Новый функционал — с примером в `guide/` (его выполнит `tests/test_guide.py`)
   и строкой в CHANGELOG.
6. Делаем только то, в чём уверены и что можно проверить измерением. Идеи без
   уверенности — в раздел «Не делаем» с причиной; возвращаемся к ним, только
   если данные (например, с Pi) покажут, что они нужны.

## Релиз 0.6.2 — исправления позы и доступность

### R2. Поза по всем найденным уровням; исправить масштаб запасного пути `[ext P0-1]`
**Баг:** без inner points `estimate_pose` считает `corners[0]` внешним квадратом
со стороной `marker_size`. Если виден только внутренний уровень, масштаб
ошибается во столько раз, во сколько уровень меньше внешнего (×7 для L3 у
`FRACTAL_3L_6`), а `reproj_err` этого не видит.
- [x] Запасной путь: углы **всех** найденных уровней с их настоящими
      3D-координатами из конфигурации (`keypts[0..3]` каждого уровня, в единицах
      `marker_size`), решатель `SOLVEPNP_IPPE`; один уровень — `IPPE_SQUARE`
      с его собственной стороной.
- [x] Вернуть использованный метод: `estimate_pose(..., full=True)` →
      `Pose(..., method, ...)`, `method ∈ {"inner", "corners"}`; по умолчанию
      прежний кортеж из 3 элементов.
- [x] Тесты: виден только L3 (точек нет) → z совпадает с истиной ±1%
      (`tests/test_pose_levels.py`). Несколько уровней без inner points
      (5L_6, наклон 0–60°, шум/размытие): глубина та же (±0.05%), поворот у
      почти фронтальной метки с шумом 0.8–1.7° → 0.02–0.05°, на наклонах без
      изменений.

**Готово, когда:** тесты выше зелёные; `detect` без inner points по-прежнему
стоит столько же.

### R13. `PoseSmoother` для управления `[ext P1-4]`
Сейчас: модель постоянного положения (отстаёт при движении), шаг не зависит от
реального интервала, нет отбраковки выбросов, `rvec` сглаживается
покомпонентно — для камеры, смотрящей вниз (угол ≈ π), это даёт скачки.
- [x] Ориентация — кватернион с выбором знака по предыдущему значению,
      фильтр в касательном пространстве (ошибка как малый вектор поворота).
- [x] Положение — состояние «положение + скорость», `update(rvec, tvec, t)`
      с меткой времени, `dt` из разности меток.
- [x] Гейтинг выбросов по расстоянию Махаланобиса; шум измерения из
      `reproj_err` и числа точек (если переданы).
- [x] Совместимость: текущие аргументы и поведение без `t` сохраняются.
- [x] Тесты: поворот на 180° вокруг оптической оси + малый шум → сглаженный
      `rvec` не скачет; движение с постоянной скоростью → отставание ≈ 0;
      одиночный выброс игнорируется.

### R14. Устойчивое решение позы `[ext P2-4]`
- [x] После первого решения один раз отбросить точки с остатком

## Релиз 0.7.0 — дальность, освещение, ARM

### R16. Надёжное чтение битов и отладочный режим `[ext P0-2, P1-1]`
Сейчас ячейка читается одной билинейной выборкой в центре, порог — среднее по
всем ячейкам; на ~4.4 px/ячейку и при резкой тени чтение ломается.
- [x] Сначала отладочный режим: для каждого кандидата — причина отказа
      («нет четырёхугольника», «мало контраста», «рамка не чёрная», «биты не
      совпали»). Им подтвердить, что на дальних кадрах с Pi отказ именно в чтении.
      *Сделано:* `FractalDetector.diagnose()` — причина (`accepted`/`duplicate`/
      `border`/`bits`), ближайший код, число неверных бит рамки и данных,
      контраст ячеек; горячий путь не тронут (скорость в пределах шума).
- [x] Второе чтение отвергнутых четырёхугольников. `diagnose` на синтетике
      показал: вдали четырёхугольник находится, ломается чтение, и главная
      причина — эталонный `getSubpixelValue` берёт выборку до пикселя мимо
      центра ячейки (при 2–4 px/ячейку это соседняя ячейка). *Сделано:*
      точная билинейная выборка центра ячейки, при неудаче — углы через
      `cornerSubPix`; только если эталонное чтение не расшифровало ни одного
      размера сетки, с отсечением однотонных пятен (контраст < 40) и
      `cornerSubPix` только при почти чёрной рамке. Уровни, найденные эталоном,
      сохраняют углы бит-в-бит; эталонный тест теперь «эталон ⊆ наше».
      Синтетика `benchmarks/reading.py` (`FRACTAL_4L_6`, кадр 1280×720,
      blur 0.6, шум 3, наклон, фон с мусором), доля кадров с внешним уровнем:
      2.2 px/ячейку 0 → 42 %, 2.6 → 0 → 80 %, 3.0 → 0 → 100 %,
      3.5 → 27 → 100 %, 4.4 → 85 → 100 %. Ложные: 0 из 300 кадров с
      3600 похожими на метку объектами (случайные коды с рамкой, метки других
      конфигураций). Скорость на 1 ядре ×0.95–1.04 (шум). `robustness.py`:
      только новые уровни (blur σ=2, наклон 45–60°, метки 120–200 px).
- [ ] Медиана центральной области ячейки, Otsu с повторами (×0.7, ×0.45),
      несколько выборок на ячейку: на той же синтетике **не дали прироста**
      (2.6 px/ячейку: 77–80 % против 80 %), только +50 % времени на мусоре.
      Не включены; вернуться, если кадры с Pi покажут неудачи с низким
      контрастом или градиентом внутри метки.
- [ ] Тень: на синтетике (тень ×0.3, мягкий край 2 px) отказ не в чтении —
      нет четырёхугольника (край тени сливается с рамкой в пороге), это
      порог/контуры, а не R16. ×0.6: 98 %, ×0.45: 95 %, ×0.3: 0 %.
      См. «Не делаем»: несколько размеров блока порога — по данным с Pi.

**Готово, когда:** сценарий `nadir h=4.4 м` (2.6 px/ячейку) ≥ 90%, `shadow` ≥ 98%,
0 ложных поз на наборе без метки, скорость `detect` не хуже −10%.
*Статус:* на синтетике 2.6 px/ячейку — 80 % (цель 90 %), 3.0 — 100 %;
ложных 0; скорость в норме; тень — не закрыта (причина вне чтения).
Приёмка — на кадрах с Pi (RPI_TEST_PLAN, разделы E, J).

### R18. Проверка согласованности уровней `[ext P2-2]`

      0 отброшенных настоящих уровней на 696 кадрах (все конфигурации,
      дисторсия, дальние метки); скорость в пределах шума.
- [x] Тест: подложить ложный кандидат с правильным id в другом месте → отброшен

### R6. Масштаб в трекере без потери точности
- [x] Уточнение углов coarse-to-fine по пирамиде (Romero-Ramirez 2018),

      *Сделано:* замер показал, что пирамида не нужна — углы уже уточняются

      0.518 px — абсолютные 0.45 px не достигает и сам полный кадр на этой
      синтетике с blur 0.8 и шумом).

**Готово, когда:** ×3+ на 4K, ошибка углов ≤ 0.45 px на синтетическом видео.

### R7. Порог на 4K
- [x] Тайлы по строкам + слияние с масками соседей; −30% времени порога, бит-в-бит.
      *Сделано:* замер (4K, 1 ядро): порог 4.5 мс, из них горизонтальные
      суммы 2.5 (разложение по степеням двойки, ~9 проходов), плюс отдельный

      Бит-в-бит с `cv::adaptiveThreshold` (новый прямой тест, k = 3…255).

## Не делаем (пока)

| Идея | Почему нет |
|---|---|
| Восстановление по признакам шаблона (ORB/AKAZE + RANSAC) `[ext P1-2]` | Прикладной уровень, риск уверенных ложных поз; нужна отдельная валидация. Вернуться, если после R16 перекрытия останутся главной причиной потерь на Pi |
| LK-сопровождение в `FractalTracker` `[ext P1-3]` | Прикладной уровень; смешивает «детекцию» и «сопровождение». Потребитель может строить его на `points_2d` |
| Метка времени в `DetectionResult` `[ext P2-3]` | Время кадра знает вызывающий код, не библиотека |
| Несколько размеров блока адаптивного порога параллельно | Каждый размер — ещё один проход порога и трассировки; вернуться, только если R16 не закроет тени |
| Увеличение изображения для мелких меток | Не уверены в выигрыше; проверить только если R16 не даст дальность |
| Чтение битов по периметру ячейки (Recursive ArUco) | Для фрактальных меток выгода не доказана |
