# План испытаний nanofractal на Raspberry Pi 5

Для чего: получить данные, которых нет в синтетике и в CI, и приёмочные цифры
для задач из [ROADMAP.md](ROADMAP.md). Каждый раздел говорит, что мерить, как
и что прислать. Базовая версия для сравнения — `nanofractal==0.6.1`; после
каждого релиза тот же прогон повторяется.

Обозначения: **R…** — задача в ROADMAP, ради которой нужен раздел.

## 0. Подготовка (один раз)

- Pi 5, Raspberry Pi OS Bookworm **64-bit** (колёса только aarch64), Python 3.11.
- Активное охлаждение; блок питания 27 Вт.
- Записать окружение:

```bash
python -m pip install nanofractal==0.6.1
python - <<'EOF' > env.txt
import platform, nanofractal as nf
print(platform.platform(), platform.python_version())
print("nanofractal", nf.__version__, "OpenCV", nf._opencv_version(), "threads", nf.get_num_threads())
EOF
cat /proc/cpuinfo | grep -m1 -i model >> env.txt
vcgencmd version >> env.txt; vcgencmd measure_clock arm >> env.txt
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor >> env.txt
```

- Для замеров скорости: `performance` governor
  (`echo performance | sudo tee /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor`),
  остальные процессы не запущены; отдельно — замеры под реальной нагрузкой (раздел C).
- Метка: **FRACTAL_3L_6**, 180 мм (как в отчёте) и, если возможно, ещё
  **FRACTAL_5L_6** того же размера — для сравнения дальности уровней.

## A. Корректность на aarch64 (CI проверяет только одну версию Python под QEMU)

```bash
git clone https://github.com/Onikore/nanofractal && cd nanofractal
git checkout v0.6.1
python -m pip install pytest numpy
python -m pytest tests -q --ignore tests/test_benchmarks.py
```

Ожидание: все тесты зелёные, в том числе `test_reference_equivalence.py`
(углы бит-в-бит с эталоном и трассировка = `findContours`).
**Прислать:** вывод pytest.

## B. Скорость по стадиям и разрешениям (R4, R5, R7)

```bash
for t in 1 2 3 4; do
  python benchmarks/fractal_bench.py run --threads $t \
    --resolutions 640x480 1280x720 1920x1080 --json pi_t$t.json
done
python benchmarks/fractal_bench.py run --resolutions 1280x720 --batch --json pi_batch.json
```

Плюс профиль, чтобы увидеть, какие стадии дороже всего на ARM (это решает,
нужен ли NEON и где):

```bash
sudo apt install linux-perf
perf record -g -o pi.perf python -m nanofractal.bench --resolution 1280x720 --frames 2000 --scene perspective
perf report -i pi.perf --no-children --sort symbol --stdio | head -40 > pi_profile.txt
```

**Прислать:** `pi_t*.json`, `pi_batch.json`, `pi_profile.txt`.

## C. Реальная нагрузка и задержка (R15)

Конвейер, как в полёте: захват IMX296 + детекция + поза + (кодирование/превью).

- `set_num_threads` = 1, 2, 3, 4 × с превью/кодированием и без.
- На каждый вариант 5 минут: кадров/с, задержка «захват → поза»
  p50 / p95 / p99, пропущенные кадры.
- Вариант с `FractalTracker` против `detect()`.

**Прислать:** таблицу (CSV) с этими колонками.

## D. Длительная работа и нагрев

- 30 минут непрерывно на 1280×720, все потоки: каждые 10 с записывать
  кадров/с, `vcgencmd measure_temp`, `vcgencmd get_throttled`, RSS процесса.
- 2 часа: только RSS и отсутствие падений (поиск утечек).

**Прислать:** CSV временного ряда.

## E. Дальность и чтение битов (R16 — главный приёмочный тест)

Съёмка сверху (nadir), метка 180 мм, высоты 1.5 … 5.0 м с шагом 0.4 м
(px/ячейку из отчёта: 2.6 м → 4.4, 4.4 м → 2.6). На каждой высоте:

- 20 кадров в неподвижности и 20 с покачиванием (как в полёте);
- доля кадров с найденной меткой, какие уровни найдены, ошибка позы (если есть
  ground truth — раздел J);
- те же кадры с `adaptive_c` = 3, 5, 7 и `adaptive_block_size` = 9, 15, 21.

Важно сохранить **сами кадры** на высотах 3.0–5.0 м: после R16 прогоним по ним
новый декодер и отладочный режим (причины отказа).

**Прислать:** таблицу и кадры (PNG без сжатия, ≥ 50 штук на 3.0–5.0 м).

## F. Освещение

На 1.0 м и 2.5 м, по 30 кадров:

1. резкая тень через метку (как в отчёте: 35% яркости);
2. мягкая тень, облачность;
3. прямое солнце, блик на метке (глянцевая и матовая бумага);
4. контровой свет (солнце в кадре или рядом);
5. сумерки: автоэкспозиция и фиксированная короткая выдержка (шум усиления);
6. мерцающее светодиодное освещение (в помещении).

Метрики: доля детекций, ошибка позы, `reproj_err`. **Прислать:** таблицу и
по 5 кадров на сценарий, особенно неудачных.

## G. Движение (смаз)

IMX296 — глобальный затвор, поэтому важна только выдержка.

- Выдержки 1, 2, 4, 8 мс × горизонтальная скорость 0.5 / 1 / 2 м/с на 1.5 м
  (или вращение камеры с известной угловой скоростью).
- Доля детекций и ошибка позы.

## H. Перекрытия

На 1.0 м, по 30 кадров:

- полоса 10 / 20 / 30% стороны с каждой стороны метки;
- закрыт один угол внешнего уровня;
- закрыт центр (круг 50 мм);
- центр + угол (сценарий, где 0.6.1 даёт 0%);
- случайные пятна 10 / 20 / 30% площади;
- реальная помеха: опора/ножка аппарата, тень винта.

Метрики: доля детекций, какие уровни найдены, ошибка позы.
Нужно, чтобы решить, возвращаться ли к восстановлению по признакам шаблона
(сейчас в «Не делаем»).

## I. Ложные срабатывания и несколько копий (R8a, R16, R18)

- **Без метки:** ≥ 30 минут видео над разными поверхностями — трава, асфальт,
  гравий, плитка, разметка, решётки, крыши, текст и QR-коды.
  Считать ложные детекции (любой id) и ложные позы. Этот прогон обязательно
  повторяется после R16: многопороговое чтение не должно добавить ложных.
- **Две копии** FRACTAL_3L_6 в кадре: что возвращается сейчас; после R8a —
  что `multiple_instances = True`.
- **Метка другой конфигурации** (например FRACTAL_5L_6 при детекторе 3L_6) —
  не должна находиться.

## J. Точность позы с эталоном и данные для R2 / R13 / R14 / R20

Эталон: шахматная доска на одной плоскости с меткой (или точная
механическая установка), поза доски через `cv2.solvePnP`.

- Дистанции 0.1 / 0.3 / 1 / 2 / 3 м × наклон 0 / 15 / 30 / 45 / 60°.
- Для каждого кадра записать: позу nanofractal `detect()` (без inner points),
  `detect(with_inner_points=True)`, эталон; `reproj_err`, число точек.
- Отдельно (**R2**): кадры, где виден только внутренний уровень (камера близко,
  внешний за кадром) — зафиксировать ошибку масштаба 0.6.1, это регрессионный
  тест для исправления.
- Отдельно (**R13**): запись потока поз при взгляде вниз (угол ≈ π) с
  `PoseSmoother` и без — видны ли скачки `rvec`.
- Отдельно (**R14**): кадры на 0.1 м, где RMS большой при верном положении
  (неплоская бумага, край кадра).
- Отдельно (**R20**): фронтальная метка малого размера (30–60 см) — как часто
  IPPE выбирает «не ту» гипотезу наклона (сравнить с эталоном/IMU).

**Прислать:** кадры + эталонные позы в формате `benchmarks/real_images`
(manifest.json: путь, конфигурация, ожидаемые id, поза, размер метки,
калибровка камеры). Это станет набором R9.

## K. Камера и калибровка

- Сравнить детекцию на сыром кадре с дисторсией против выпрямленного (`remap`):
  скорость полного конвейера и точность позы. Ответ нужен для рекомендаций в
  `guide/` (выпрямлять кадр или передавать коэффициенты дисторсии).
- Разрешения 640×480 / 1280×720 / 1456×1088 (полное IMX296): дальность против
  задержки.

## Что прислать и как

- Один архив на прогон: `env.txt`, JSON/CSV из разделов, кадры неудачных
  случаев, краткая заметка об условиях (погода, высота, скорость).
- Скрипт `tools/bench_nanofractal.py` и сцены из отчёта — мы перенесём их в
  `benchmarks/` как приёмочные тесты (R9).

## Порядок проведения

1. **A, B, C** — до начала работы над 0.6.2/0.7.0 (базовые цифры).
2. **E, I, J** (включая отдельные случаи для R2/R13/R14) — до реализации R16 и
   исправлений позы: это приёмочные данные.
3. **F, G, H, K** — по мере возможности; решают судьбу пунктов из «Не делаем».
4. После каждого релиза — повторить A, B, E, I на новой версии.
